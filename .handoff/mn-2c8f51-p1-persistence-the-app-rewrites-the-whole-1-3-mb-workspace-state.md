### What is durable when

- Database: a flush that wrote anything is on disk when `save` returns, synced with F_FULLFSYNC (`synchronous = FULL` + `fullfsync = ON` on the writer). Before, the same flush became durable at the close checkpoint's F_FULLFSYNC at the end of the same call, so promptness is equal; between flushes nothing was ever synced before either. Checkpoints no longer gate durability: they fold the WAL into the main file at the library's 1000-frame threshold, off the main thread, and at an orderly quit. A kernel panic or SIGKILL at any moment leaves the last committed flush recoverable from the WAL (SQLite recovery on the next open, exercised by the tests below).
- `workspace-state.json`: written atomically (temp file + rename, unsynced, exactly as before) whenever the durable state changed and once at an orderly quit. Never on a per-poll flush.
- Liveness ledger (`restore-liveness-ledger.json`) and restore run log (`restore-runs.json`, lane mn-3c4b23): not touched; they keep their own temp-file + F_FULLFSYNC + rename writer (`HolyRestoreFileCoding.writeDurably`) and are written by Workspace/, outside this path.
- `HolyDatabaseCompactor` (launch-time and "Compact Database Now") still works with the writer open and idle: proven by `inPlaceCompactionSucceedsWhileTheDurableWriterIsOpen`.

### How crash restore was proven

- `committedFlushSurvivesTheWriterDyingBeforeAnyCheckpoint`: a real save through `HolyWorkspaceDatabaseWriter` (checkpoint count 0, writer still open, `-wal` non-empty), then the bytes a SIGKILL leaves (main file + WAL, no `-shm`) are copied to a fresh directory and opened with the production loader: sessions, selection, templates, archive rows with git state, attention metadata, and the live preview text all come back. The main file alone does not carry the flush, which is why the commit sync is the durability point.
- `flushKilledBeforeCommitLeavesThePreviousFlushIntactAndTheWriterRecovers`: the production save path executes every statement of a second flush and is stopped at the instant before COMMIT by `sqlite3_commit_hook` (which snapshots the on-disk bytes and vetoes, SQLite's ROLLBACK): the crash copy and the live database both load the previous flush; the writer drops its connection, the next save reopens (`connectionOpenCount` 2) and lands the second state.

### Risks and what is left

- Main-thread cost per flush that wrote something is now one F_FULLFSYNC of the WAL (a few frames) instead of a whole-file checkpoint; a flush that wrote nothing costs the conditional statements only (no sync). If the orchestrator's `wal_kb_per_s` is unexpectedly high, the per-row writers are `latest_preview_text` and `updated_at` on active rows (they change with every poll that produces output), and the next lever is the supervisor's cadence, deliberately not touched here.
- The JSON's active-record `updatedAt` lags between durable changes (exact again at quit or on the next change). It is read only when the database has no initialized workspace, and only as a fallback anchor there.
- `HolyWorkspaceDatabaseWriter.shared` keeps the app database open for the process's life; short-lived connections elsewhere (task, profile, remote-host, inbox, board writers; retention on the utility queue) no longer get the close checkpoint either, which is intended: their frames fold at the same threshold or at quit. The first launch of this build folds whatever WAL the previous build left at its next checkpoint.
- The checkpoint queue keeps its own connection open after the first checkpoint; `HolyDatabase.close()` shuts it down synchronously and must not be called from that queue (documented on `shutdown()`).
- `HolyDatabaseCheckpointPolicy` replaces SQLite's built-in auto-checkpoint hook on the writer only; the threshold is the value the library reported, so a future library default changes the schedule with it.
- Retention now runs after flushes that wrote rows and once after launch; a backlog can only be created by a flush, so nothing waits longer than before.
- Sealing (`agent-do manna handoff seal mn-2c8f51`) and `manna claim/done` are the orchestrator's per lane rules; this file's `binding:` hash is stale until resealed. No push, no installer, no board command was run.
